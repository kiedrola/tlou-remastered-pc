   statically to enumerate **every** external dependency and *how* it is consumed
   (`pkg-config`, `find_package`, `find_program`, submodule, or vendored in the repo).

   uses, CMake config packages under `/usr/{lib,share}/cmake`, tools on `PATH`, and the

3. Ran a **fresh out-of-tree CMake configure** (`cmake -S gpu -B /tmp/gow3-task02-verify`)
   plus the `host_shaders` target, to prove every `REQUIRED` find resolves and `glslang`
   works end-to-end (31/31 shader headers generated).
4. Compared the resulting list with the MSYS2 packages in
   `gow3_pc/packaging/windows/README.md` and documented it in

## The roadmap's list: what held, what did not

The roadmap listed 16 packages. **12 are required** (the table above, minus the build
tools). The other 4 are **not needed by the build**:

- `spirv-cross` — used only by the optional asset tools (`tools/fsr4_optimize.sh:23`,
  `tools/fetch_fsr4_assets.sh:35`). The build never calls it: shader→header conversion is
  `glslang`, and dynamic SPIR-V assembly uses `sirit`, a self-contained runtime assembler
  (CMakeLists:96 forces `SIRIT_USE_SYSTEM_SPIRV_HEADERS OFF`, so `externals/SPIRV-Headers`
  is used, not a system package).
- `xbyak` — header-only and consumed from the submodule (`target_include_directories
  ... third_party/xbyak`); it is not packaged for Arch at all (checked against the repos).
- `libxcb`, `wayland` — not referenced by `build.sh` or `CMakeLists.txt`; they are present
  in `shell.nix` and are needed only at **runtime** by SDL3's Wayland path (and the Vulkan
  ICD loaders). Same for `xorgproto` (a build-time dep of `libxcb`/`wayland` packages).

**Missing from the roadmap's list (required, now documented):** `base-devel` (the C
compiler), `cmake`, `ninja`, `pkgconf`, `git`. `python`/`python3` is needed by `tools/`
and the launcher (Tasks 9-10), not by `build.sh` — it is listed in `shell.nix` for that.

## Technical decisions and observations

1. **New doc: `gow3_pc/packaging/linux/README.md`.** It mirrors the Windows twin
   (`packaging/windows/README.md`) in structure: short intro, one install block, the
   submodule note, the build command, and the extra platform-specific notes. It documents
   *what to install*; the evidence and the MSYS2 comparison live in this report.
2. **`vulkan-memory-allocator` is the fragile one.** On this machine it is installed
   (3.5.0-1) but **absent from the sync database** (`pacman -S` cannot install it here; on
   standard Arch it is in `extra`). The build resolves it through the CMake CONFIG package
   the distro package ships. Note the header-only fallback in `gpu/CMakeLists.txt:68-75`
   searches `PATH_SUFFIXES vma` — that matches the **MSYS2 layout**
   (`include/vma/vk_mem_alloc.h`); Arch installs the header at
   `/usr/include/vk_mem_alloc.h`, so on Arch the CONFIG package is the supported path.
   Left as-is: the fallback exists for MSYS2, and touching shared CMake would violate the
   "do not move the Windows branch" rule for no gain.
3. **The `build.sh:60` guard is satisfied on Arch** (`pkg-config --exists vulkan sdl3` +
   `cmake` + `ninja` all present), so the automatic `nix-shell` reactivation
   (`build.sh:61-62`) stays cold; `shell.nix` remains the reproducible fallback (Plan B).
4. **`shell.nix` vs. reality:** it lists extras the build does not need
   (`magic-enum`, `miniz`, `xbyak`, `spirv-cross`, `spirv-headers`, `libxcb`, `xorgproto`,
   `wayland`, `gnumake`, `python3`). All are harmless (the submodules win for
   magic_enum/miniz; the rest are runtime/tooling). Not trimmed: `shell.nix` is the
   NixOS/Plan B environment and extra packages are free insurance, and changing it cannot
   break Windows.
5. **Version drift is benign.** A few installed packages lag the current repo versions
   (SDL3 3.4.18 vs 3.4.20, FFmpeg 9.0.2-2 vs -5, libx11 1.8.13 vs 1.8.14); the build and
   the Task 1 smoke tests pass with the installed versions.
6. **Windows compatibility:** documentation-only task. Zero changes to `build.sh`,
   `CMakeLists.txt`, or any source: the Windows build is provably untouched.
